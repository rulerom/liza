# Performance Parity — инженерная цель и JSON P0

Цель Liza — не менее **90% throughput Rust** на согласованном наборе эквивалентных
системных алгоритмов при сопоставимых гарантиях и условиях измерения. Это критерий
зрелости, **не текущий результат и не рекламное обещание**. Публикуются результаты
каждой нагрузки: среднее не должно скрывать устойчивое отставание в 2–3 раза.
Отклонения требуют измеренного объяснения; случайный CI runner не служит стендом
для жёсткого performance threshold.

Обязательные ограничения: сохраняются checked-traps и порядок эффектов,
независимость `copy`, явные ограничения памяти и стоимости. Проверку можно
устранить только при установленной избыточности. Скорость не заменяет корректность.

## Направления

| Направление | Предмет | Следующий критерий |
| --- | --- | --- |
| P1: JSON | IR, ARM64, inlining, checks, SSA, layout | Изолированные эксперименты на неизменном корпусе |
| P2: networking | Заголовки, буферы, generation tables, reactor, relay | Разделить приложение/ОС; throughput, p50/p99, CPU/Гбит/с, syscalls, память/пару |
| P3: aggregates | Destination propagation | Проверить snapshots и traps; не считать решением mutable JSON заранее |

Эти направления не меняют приоритет эксплуатационной надёжности Network Gateway.
Первая диагностика называется **Performance Parity P0 — JSON ARM64 Investigation**;
обозначение P0 здесь — номер исследования, а не перенос сетевых задач на второй план.

## Зафиксированный эксперимент P0

Компилятор/stdlib: `899855a4833dd43e32398eed65401888bb7883c8`.
Исходники Rust и исходного baseline сохранены из существующего стенда;
база исходного JSON — `b3206117a225f6f852cec5bef18928fe1bd43856`.
Apple M4, Apple Clang 21, rustc 1.99.1, generic CPU, O2, без LTO через общий C ABI.
Rust собран с `overflow-checks=yes` и `panic=abort`. Сохранены версии и команды.

Все эксперименты меняют только `alwaysinline` в исследовательской копии LLVM IR.
Core, runtime, алгоритм JSON и рабочий backend не меняются. Выбор функций по именам
разрешён для диагностической абляции; он не предлагается как политика компилятора.

| Вариант | Изменение относительно M0 |
| --- | --- |
| UTF8 | Встроить `utf8_stream.feed_byte` |
| Step | Встроить `__liza_json_mut_step` |
| Done | Встроить `__liza_json_mut_done` |
| Combined | Встроить все три |

Перед измерением: 6785 chunk-partition случаев с независимыми ожидаемыми исходами
и byte offsets на каждый executable; пять вариантов на O0/O2 плюс Rust;
1476 CLI-проверок, включая исходный CLI. Отдельно проверен весь timing corpus.
Четыре теста диагностического инструмента включают нативную проверку счётчиков
входа в функции. Это не доказательство для всех состояний JSON или всего LLVM.

## Измерения

Шесть документов ~256 КиБ, чанки 2048 байтов, десять перемешанных серий,
360 samples. Один прогрев перед каждым измерением; ~16 МиБ на sample.
Инициализация/feed/finish включены, ввод файла и выделение входного буфера — нет.
В старом M0 отчёте sample был ~4 МиБ: для отношений используются одновременные
контроли M0/Rust, а не исторические цифры. Значения ниже — медианы, МиБ/с.

| ascii | 200.4 | 236.0 | 259.6 | 234.5 | 311.0 | 436.5 | 71.3% |
| unicode | 228.2 | 265.8 | 303.7 | 247.3 | 380.4 | 547.1 | 69.5% |
| escaped | 215.8 | 260.9 | 267.6 | 241.8 | 338.3 | 492.6 | 68.7% |

с зафиксированным harness, без выбора лучших значений из разных запусков.

## Что установлено по IR и assembly

**1. Граница UTF-8 helper.** В M0 `stream_feed` на каждом байте вызывает
`liza_utf8_stream.feed_byte`. Перед вызовом грузятся поля `Utf8StreamState`,
после него сохраняется возвращённое состояние. В соответствующем ARM64 участке
есть семь load-инструкций для полей (одна `ldp` читает два поля), семь store-инструкций
результата (одна `stp` пишет два поля) и сохранение аргумента byte на стеке.
Это скалярный трафик, который счётчик `memcpy/memmove` не учитывает.
UTF8-абляция ускоряет все шесть нагрузок, но её эффект включает последующие
оптимизации LLVM, а не только удаление `bl`.

**2. Граница JSON step.** Второй вызов на каждом байте —
`liza___liza_json_mut_step`. После него цикл заново читает код ошибки и position.
В Rust переход JSON и UTF-8 встроены в `stream_feed`. Step-абляция также даёт
устойчивый выигрыш. Порядок checks/updates сохранён в исходном IR эксперимента;
обязательная overflow-проверка увеличения position остаётся в optimized IR.

**3. Цикл и completion helper.** На ASCII счётчики оптимизированного IR дают
ровно 1 вход в UTF-8 helper и 1 вход в step на байт; `done` — около 0,075 входа/байт.
При Combined внутри побайтового пути эти вызовы исчезают, но остаётся вызов
обработчика чанка. Отдельный Done меняет также layout/inlining других участков:
его выигрыш даже на long-string нельзя приписывать только редким вызовам `done`.
Скоростные эффекты абляций не складываются.

Независимый пятисекундный `sample` на ASCII локализует горячую работу M0 в step,
`stream_feed` и UTF-8 helper; у Rust почти всё время находится внутри `stream_feed`.
Профилирование выполнялось после timing, его throughput не входит в таблицу.
Счётчики и sampling не являются точным подсчётом исполненных машинных инструкций,
циклов, branch misses или трафика кэша на байт.

Frame `liza_json.feed_mut` увеличивается с 64 до 96 байт при Combined.
В Combined `stream_feed` превращается в tail-переход к этому callee: его собственный
нулевой frame нельзя объявлять нулевым стеком обработки. Уменьшение frame не было
условием ускорения. Размер состояния Liza — 184 байта, Rust — 176; layout не
контролировался отдельной абляцией и остаётся возможным фактором.

## Что ещё не установлено

Найдены три горячих участка и измерены эффекты границ встраивания, **не доказаны
три независимые крупнейшие причины всего отставания**. Остаток до Rust требует
следующего исследования: точные динамические ветвления/загрузки в Combined,
формирование `Option/Result`, удержание полей в регистрах, layout и доказуемо
избыточные bounds/overflow guards. Наличие инструкции в assembly не доказывает
её доминирующую стоимость.

Не включать безусловный `alwaysinline` в backend по этому отчёту. Сначала выбрать
общую ограниченную политику, проверить рост кода и другие программы, snapshots,
порядок traps/эффектов и платформенную регрессию. Проверки не отключать.

# Performance Parity P1 — ограниченная политика inlining

Исследование на Apple M4 продолжает [JSON P0](performance-parity.md).
**Рабочий backend, Core, runtime и JSON-алгоритм не изменены.**
Проверены штатные пороги LLVM и ограниченный выбор inline hints по Semantic IR.
Результат — кандидат для дальнейшей приёмки, не автоматически включённая оптимизация.

## Решение

Порог LLVM **400** вместо default 225 на зафиксированном Clang улучшает все шесть
нагрузок на 8–30%. Он проходит выбранные ограничения `.text` и frames для JSON,
полного RTP parser, relay и отрицательного примера роста кода.
IR-guided вариант даёт близкую скорость; усложнять компилятор этим анализом пока
не предлагается. Пороги 600/3000 не проходят бюджет JSON.

**Большая часть выигрыша P0 в этом бюджете пока не получена.** Порог 3000 иногда
приближается к P0 control, но удваивает `.text` JSON и раздувает отрицательный
пример в 35 раз. Это не основание ослабить бюджет или включить `alwaysinline`.
Паритет с Rust не достигнут.

## Что сравниваем

| Стратегия | Настройка |
| --- | --- |
| Default | LLVM O2 без дополнительных флагов |
| Cost 400/600/3000 | `-mllvm -inline-threshold=N -mllvm -inline-max-stacksize=256` |
| Guided | `inlinehint` для небольших функций; `inlinehint-threshold=600`, callee stack limit 256 |
| Excessive | `inline-threshold=50000`, отрицательный контроль |
| P0 control | Предыдущие три name-selected `alwaysinline`, только контроль в той же серии |

Cost-based политика не читает имена функций. Guided выбирает вызываемые функции
с pure effect contract, не более 160 Semantic IR operations и 64 blocks, без циклов
CFG и рекурсивного call closure. LLVM решает, применять ли hint. Проверяется, что
остальные инструкции IR не изменены. Выбор тестируется с переименованными функциями.
`pure` здесь — критерий отбора, а не предположение об отсутствии mutable-записей.

Guided изучен после предварительного sweep: штатный порог, близкий по скорости
к P0, нарушил ограничение роста кода. Это исследовательские cutoffs, не универсальная
модель стоимости. Названия JSON-функций есть только в отдельно обозначенном P0
контроле; они не участвуют в двух новых политиках.

## Ограничения и фактический fallback

Кандидат сравнивается с объектом Default той же программы:

- Размер секции `__TEXT,__text` — не более 125% Default.
- Frame каждой функции — не более `max(256, 2 × default_frame)` байт.
- Неизвестные/dynamic frame records прерывают этот диагностический запуск.

При нарушении бюджета в `selected.o` копируется объект **Default**, а не отвергнутый
кандидат. Проверены совпадение байтов и хешей всех выбранных объектов. Негативная
мутация, разрешающая заведомо чрезмерный рост, обнаруживается отдельной проверкой.

Лимит callee stack в LLVM не ограничивает общий стек вызовов. Frame-проверка тоже
не доказывает peak stack всей программы. Размер объектной секции включает
сохранённые функции; это не измерение I-cache misses и не полный размер бинарника
с runtime. Время компиляции измеряется отдельно; жёсткой границы времени здесь нет.
Два построения для сравнения добавляют стоимость и пока не включены в production.

## Скорость JSON

один прогрев перед sample, ~16 МиБ на измерение, 10 перемешанных серий.

## Размер кода, стек и компиляция

Числа ниже — байты секции объекта, до линковки с runtime.

| Программа | Default | Cost 400 | Cost 3000 | Guided | Excessive |
| --- | ---: | ---: | ---: | ---: | ---: |
| JSON | 7320 | 8036 | 14932 | 7700 | 14932 |
| RTP parser | 1048 | 896 | 1356 | 1356 | 1356 |
| TCP relay | 23384 | 23504 | 23932 | 23384 | 77220 |
| Growth control | 1852 | 1852 | 65016 | 1852 | 65016 |

Guided меньше Cost 400 для JSON, но нарушает бюджет RTP и там откатывается.
Excessive увеличивает relay в 3,3 раза. Синтетический Liza growth control содержит
48 различных вызывающих функций и один чистый helper с 64 ветвями; его 35-кратное
раздувание отклоняется. Это реальный отрицательный контроль code growth, **не
эксперимент, доказывающий ухудшение I-cache**.

Frame `json.feed_mut` для Default/Cost 400 — 64/80 байт; frame `step` — 32/32.
`stream_feed` становится tail-переходом: его frame 0 не означает нулевого стека
обработки. Максимальные отдельные frames модулей JSON/RTP/relay — 784/64/4720 байт
и при Cost 400 не увеличиваются. Проверка ведётся по каждой функции, чтобы большой
чужой frame не скрывал рост маленькой функции.

| Компиляция объекта, медиана 3 тёплых запусков, мс | Default | Cost 400 | Cost 3000 |
| --- | ---: | ---: | ---: |
| JSON | 73.4 | 78.6 | 118.0 |
| RTP | 20.2 | 19.5 | 21.0 |
| Relay | 197.0 | 202.8 | 202.8 |
| Growth control | 24.6 | 24.8 | 208.2 |

Это descriptive wall-clock наблюдения, без frontend/link и без доказательства
значимости небольших различий. Для фактического двухпроходного gate стоимость
Default надо **добавить** к кандидатной, а не скрыть её за последним столбцом.

## Приёмка и границы

- Все шесть стратегий на O0/O2 и Rust: 6785 partitioned cases на executable,
  независимые expected outcomes/offsets; 1722 CLI checks; полный timing corpus.
- Cost 400: 30 существующих тестов snapshots, обязательных traps, порядка effects,
  RTP и реальных TCP-сокетов с fault injection. Wrapper зарегистрировал 37 O2
  компиляций с кандидатными флагами; O0 оставлен контрольным.
- 6 тестов policy: rename independence, CFG switch backedge, рекурсия, границы
  text budget, новые и скрытые большими соседями frames.
- Проверены actual fallback objects и мутация отключённого gate.

RTP и relay проверены на корректность и стоимость компиляции/кода, **не на throughput
или p99**. Это остаётся задачей отдельного сетевого baseline. Платформенная приёмка
кандидатных флагов Linux/Windows ещё не выполнена; внутренние LLVM options могут
различаться между версиями. Тесты не доказывают корректность всех LLVM-преобразований.

## Следующее решение

Cost 400 — более простой кандидат, чем Guided, но ещё не production default.
Перед включением нужны кроссплатформенная приёмка, согласованная реализация бюджета
и оценка полной цены дополнительной компиляции. Остальной разрыв следует исследовать
в generated CFG и регистровом размещении, не отключая bounds/overflow checks.
Для большего inlining потребуется ограничение дублирования кода по callsites;
глобальное увеличение порога эту задачу не решает.

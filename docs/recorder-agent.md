# Recorder Agent

Экспериментальный агент Liza принимает `recording.start` через CAN/WSS,
запускает существующий нативный VideoGrace Recorder и публикует один MP4/M4A
в Storage через HTTPS. Код Python-сервисов не меняется. Нужен актуальный
Recorder с поддержкой `--stop-file` и `VG_ACCESS_TOKEN`.

## Сборка и запуск

Для сборки необходимы Clang и OpenSSL 3, как для [TLS-клиентов](tls-transport.md).

```sh
python3 -m liza build --project-root examples \
  examples/apps/liza_recorder.liza -o liza-recorder
```

Пример локальной конфигурации:

```json
{"output_dir":"/var/lib/liza/recordings","local_only":false,"ack_ms":15000}
```

Родительский каталог должен существовать. `output_dir` — абсолютный UTF-8 путь
до 96 байт. Токен CAN хранится отдельным файлом с ограниченными правами.

```sh
./liza-recorder 192.0.2.10:443 demo.example.org recorder-node \
  /private/path/can-token - 900000 /absolute/path/Recorder recorder.json
```

Аргументы: числовой IPv4 с портом, проверяемое TLS-имя, node ID, файл токена CAN,
файл дополнительного CA либо `-` для системного доверия, длительность работы в
миллисекундах (100..3600000), абсолютный путь Recorder и файл конфигурации.
Адрес TCP и проверяемое имя TLS разделены; DNS resolver пока не нужен.

На Windows TLS-linker flags задают reserve основного стека исполняемого файла
8 МиБ (страницы commit по мере использования). На O0 снимки агрегатов ещё
создают крупные фиксированные кадры: в исследованной x64-сборке кадр
`recorder.child.tick` — около 2,7 МиБ. Стандартного PE reserve 1 МиБ недостаточно.
Это не `tls.managed_bytes()`. Явные stack budgets SG2 задаются отдельно;
старые native workers с default stack наследуют reserve PE-программы.
Оптимизация копирования агрегатов остаётся отдельной задачей компилятора.

Агент регистрирует роль `recorder`, capabilities `recording` и
`consolidated_native`, один активный assignment. `conference_tag`, ID сессии и
раздельные media/upload credentials приходят с заданием сервера. Параметры
`server_url`, `output_dir` или `native_recorder` из задания не управляют
исполняемым файлом и сервером агента.

## Владение и остановка

Один Reactor обслуживает WSS, HTTPS и heartbeat; дочерний процесс проверяется
через `process.try_wait`. Отдельного scheduler или вычислительного пула нет.
Токен медиа передаётся только дочернему процессу через `VG_ACCESS_TOKEN`,
не через argv или глобальное изменение окружения. Upload-токен не передаётся
Recorder и не заменяется media-токеном.

`recording.stop`, cancel, истечение `max_sec`, завершение агента и disconnect
инициируют остановку. Сначала создаётся stop-файл, через 10 секунд вызывается
terminate, ещё через 5 — kill. Владение Child сохраняется до wait/reap и close;
при невозможности reap агент не притворяется, что cleanup завершён.
После disconnect новое CAN-соединение создаётся только после cleanup ребёнка.

Выходной путь — `output_dir/job_id/assignment_id/output.mp4` (для audio-only —
`output.m4a`). Компоненты ID ограничены ASCII буквами, цифрами, `-`, `_` и
64 байтами. Существующий выходной файл не перезаписывается. Корень каталога
считается доверенным; это не sandbox против изменения промежуточных symlink.

## Подтверждённая публикация

После exit 0 требуется непустой обычный файл. Затем агент:

1. Отправляет `finalizing` и ждёт положительный ACK с текущими job/assignment ID.
2. Создаёт upload через `POST /api/storage/uploads` с отдельным upload-токеном.
3. Передаёт до 64 КиБ за PUT, соблюдая лимит сервера и проверяя точный offset.
4. Подтверждает Storage complete и отправляет `artifact_ready` со ссылкой на blob.
5. Ждёт соответствующий положительный ACK и только затем отправляет `completed`
   с `published: true`.

При ошибке/таймауте ACK, HTTPS, offset или разрыве CAN локальный файл сохраняется.
Файлы пока сохраняются и после успеха. ACK ограничен `ack_ms` (100..60000,
по умолчанию 15000), HTTP-запрос — 15 секундами, upload — 10 минутами.
Проверка сертификата и имени обязательна, перенаправления не исполняются.
Ответы ограничены 4 КиБ; требуются Content-Length, отсутствие Transfer-Encoding
и успешный HTTP-статус. TLS и HTTP-парсер используют bounded storage.

`local_only: true` — отдельный диагностический режим. Он отвергает задания с
обязательным Storage и сообщает `published: false` при локальном завершении.

## Приёмка и границы

Независимый WSS/HTTPS стенд проверяет точные байты файла, heartbeat во время
передачи, чужие ACK, неверный offset и отсутствие подтверждений на O0/O2.
Живые записи `radio` на demo подтвердили локальное медиа и серверную публикацию.
После исправления мелких PUT и разбора по одному байту передача 4 350 563 байт
от `finalizing` до `completed` заняла 14,381 секунды. Это одна live-приёмка,
не сравнительный benchmark.

Это узкий профиль: один файл MP4/M4A. Report/manifest/JSONL, локальный SHA-256,
возобновление upload, удаление локальных файлов и восстановление после restart
не реализованы. Native Recorder отвечает за медиакодеки; Liza — за управление,
транспорт и подтверждённый жизненный цикл. Убийство агента/машины не обеспечивает
гарантированную остановку дерева процессов.

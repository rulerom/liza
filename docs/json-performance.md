# JSON Performance Baseline

**План измерения, результатов пока нет.** Базовый исходник Liza фиксируется
на merge-коммите T2-A `b320611`; измерение не ждёт реализации T2-B.
Полный SHA коммита и SHA-256 всех входов записываются в будущий отчёт.

## Сравниваемый контракт

Основное сравнение — один потоковый алгоритм синтаксической проверки на Liza,
C++ и Rust. Реализации сохраняют состояния между чанками, предел глубины 64,
UTF-8 validation, строгие surrogate pairs, лексическую проверку чисел и абсолютные
байтовые смещения ошибок. DOM, преобразование чисел в float и скрытое накопление
токенов не допускаются. Различие принятия входа или позиции ошибки сначала
разбирается как несовпадение контрактов, а не результат производительности.

Специализированные JSON-библиотеки образуют отдельную таблицу с собственными
ограничениями и режимами; они не подменяют сравнение одинакового алгоритма.

## Воспроизводимый корпус

Генератор с фиксированным seed создаёт ASCII-объекты, Unicode, escapes и surrogate
pairs, длинные строки и числа, широкие массивы, вложенность на границе лимита.
Объёмы включают маленькие файлы и потоки значительно больше чанка 2048 байтов.
Отдельный отрицательный корпус содержит усечённые токены, неверный UTF-8,
лишние байты, повреждённые escapes и превышение глубины.

До замеров все реализации сравниваются по исходу и смещению ошибки на общем
корпусе, включая разбиения внутри UTF-8 и escape-последовательностей. Для малых
примеров проверяются все одиночные точки разбиения; для больших — фиксированные
и воспроизводимые случайные разбиения. Отрицательные входы измеряются отдельно:
быстрое отклонение в начале не считается обработкой всего файла.

## Два независимых измерения

1. **Ядро валидатора:** данные загружены заранее, одинаковые границы чанков;
   учитывается обработка данных, исключаются запуск процесса и файловый I/O.
2. **CLI:** настоящий `liza-json check` и эквивалентные C++/Rust инструменты;
   отдельно учитываются запуск, чтение файла и завершение. Тёплый файловый cache
   явно отмечается; результаты не выдаются за холодное чтение диска.

Основная конфигурация — release/O2 с записанными полными командами. O0 служит
дополнительной диагностикой. Проверки границ и переполнения не отключаются
молча ради ускорения; различия режимов безопасности явно перечисляются.

Каждая конфигурация получает прогрев и не менее 10 измеряемых повторов.
Порядок реализаций перемешивается с фиксированным seed. Сохраняются сырые времена,
медиана, разброс, MiB/s по реально обработанным байтам и доступные показатели RSS.
Аллокации ядра отделяются от запуска и файлового слоя. Результат проверки
потребляется драйвером, чтобы оптимизатор не удалил работу.

## Приёмка baseline

Отчёт содержит ОС, CPU, память, версии компиляторов, flags, SHA исходников и
бинарников, seed, хеши корпуса, размеры чанков, команды и сырые результаты.
Первое измерение на одной машине не обобщается на все архитектуры. CI проверяет
корректность корпуса и драйвера; жёсткий порог скорости на shared runners
не вводится. До появления повторяемых измерений сравнительных заявлений нет.

Следующий отдельный PR реализует генератор, эквивалентные валидаторы и драйвер.
T2-B затем сравнивается с этим неизменным baseline на той же машине и корпусе.
Это измерение стоимости, не формальное доказательство корректности алгоритма.

# Scoped channel: модель и истории операций

Это независимая **ограниченная проверка**, не доказательство потокобезопасности
всего runtime. Исполняемые модели и проверяющий код находятся в
[`verification/scoped_channel`](https://github.com/rulerom/liza/tree/main/verification/scoped_channel).
Они не импортируют реализацию канала или генератор Semantic IR.

## Модель

Абстрактная FIFO-модель хранит последовательность сообщений, состояния сторон
и числа опубликованных, прочитанных и отброшенных значений. Отдельная модель
кольца хранит слоты, head/tail, занятость, те же состояния и счётчики. Для
вместимости 1 и 2 исследуются все достижимые пары состояний за не более семи
переходов с двумя значениями отправки, приёмом и закрытием каждой стороны.
Сравниваются результаты операций и содержимое очереди; проверяются диапазоны
индексов и инвариант `published = received + discarded + queued`.

Это конечное пространство: оно не покрывает произвольные вместимости, длины
исполнения, виды значений или модель памяти C и операционной системы. Число
достижимых пар в текущей модели — 52 для вместимости 1 и 128 для вместимости 2.
Это исчерпывающий перебор **этой ограниченной модели**, не SMT-доказательство.

## Истории и runtime

Независимый linearizer принимает завершённые операции с результатами и
логическими порядками вызова и ответа. Он ищет последовательный порядок,
который сохраняет наблюдаемые результаты и не переставляет операцию за другую,
если первая завершилась до вызова второй. Отдельные тесты убеждаются, что
реальное время соблюдается и перекрывающиеся операции могут быть переставлены.

C recorder оборачивает настоящий `liza_scoped_*` из runtime: два нативных
потока записывают события до и после трёх отправок, двух приёмов и закрытия
обеих сторон. Проверяются 200 полученных историй при вместимости 2; на ошибке
тест выводит саму историю. Тестовый барьер после записи первых вызовов
принудительно перекрывает их интервалы, но сам по себе не доказывает
одновременное выполнение внутри критической секции. Глобальный атомарный
счётчик задаёт порядок записи, а барьер и запись событий меняют планирование потоков. Это выборка **только
завершённых** операций. Тест непосредственно проверяет C-ядро канала, но не
доказывает все расписания, не проверяет весь `channels.run`, компилятор или
свойства LLVM и ОС. Runtime и модель могут содержать общие ошибки постановки.

## Отрицательные контроли

В модели кольца отдельно вводятся четыре нарушения; поиск строит конкретную
последовательную историю, для которой linearizer не находит допустимого порядка:

| Нарушение модели | Пример обнаруженного несоответствия |
| --- | --- |
| Публикация повреждённого значения | Отправлено `0`, прочитано `1` |
| Нарушение FIFO | Отправлены `0`, `1`, первым прочитан `1` |
| `Full` раньше `Closed` | Заполненный канал с закрытым отправителем отвечает `Full` |
| Слот не освобождён | После чтения единственного сообщения следующая отправка получает `Full` |

Первая мутация моделирует **наблюдаемый результат** повреждённой или преждевременной
публикации; она не моделирует побайтовое перемежение внутри C-копирования.
Мутации внесены в модель, а не в production runtime. Отдельный тест runtime
из B0 проверяет намеренную порчу состояния при `Full`.

## Запуск

```sh
python3 -m unittest discover -s verification/scoped_channel -v
```

Для историй нужны Clang и поддерживаемая host-платформа. Тест собирает C с O2,
печатает найденные модельные контрпримеры и проверяет записанные истории.

# P3-P — unchanged-field forwarding в backend

Штатный LLVM backend сохраняет равенство неизменённого scalar-поля исходному
value-параметру после объединения ветвей. Это ограниченная интеграция
[P3](guard-cfg-investigation.md), без изменения синтаксиса, Core или правил traps.

```liza
struct Packet {sequence:u64;tag:u64}
fn observe(s:Packet, flag:bool)->u64 {
    var next=s
    if flag {next.tag=7} else {next.tag=8}
    return next.sequence
}
fn main()->u32 {return 0}
```

Оба входа `phi` меняют только `tag`. Чтение `next.sequence` может использовать
исходный `s.sequence`. Если на любом пути меняется `sequence`, даже за несколькими
предыдущими объединениями, forwarding не выполняется. Присваивание полю того же
значения также консервативно отклоняется: анализ не пытается доказать равенство RHS.

## Контракт и реализация

`liza/field_forwarding.py` принимает только:

- `pure`-функции с ациклическим CFG;
- неизменяемый параметр режима `value`, реально передаваемый LLVM по значению;
- копируемую плоскую структуру из integer/bool полей, не более 64 scalar leaves;
- цепочки `struct.update` других полей и `phi`, все входы которых имеют один корень.

Ресурсы, указательные/вложенные агрегаты, readonly/mutable-параметры, indirect ABI,
разные корни, неизвестные источники и функции с циклами исключены. Имена функций,
библиотек и полей в политике не используются. Проверка `large` передаётся из backend,
поэтому предположение о by-value ABI не существует отдельно от фактического lowering.

Анализ идёт в топологическом порядке, без рекурсии. Для каждого запрошенного поля
он один раз посещает операции и входы `phi`. Общие подграфы не раскрываются повторно.
Facts и certificates сохраняют корень, поле, исходный SSA-value и зависимости от
предыдущих facts. Это проверяемое основание анализа, **не независимое доказательство**.

Сохранённый Semantic IR не меняется. Backend подставляет исходный параметр только
при эмиссии scalar `extractvalue`; checked-add, trap edges и порядок операций остаются
на прежних местах. Обычный LLVM затем может устранить доказуемо избыточный guard.
Операция обновления другого поля также остаётся: её обязательный trap нельзя потерять
лишь потому, что окончательный результат читает неизменённое поле.

## Приёмка

Новые compiler tests проверяют вложенные `phi`, изменение поля на удалённом пути,
разные корни, ограничения доступа/ABI/эффектов, исключение циклов и цепочку из
250 общих «ромбов» с ограничением числа посещений анализа. Нативная проверка O0/O2
включает 66 запусков: обе ветви snapshots, обязательный overflow при изменении
другого поля и два намеренно испорченных варианта.

`tools/check_field_forwarding.py` независимо сравнивает исходный SIR с raw LLVM,
выданным production backend. Используются отдельные исполнители P3, без принятия
certificates, `may_trap` или storage summaries за аксиомы. Проверены:

- фактический `utf8_stream.feed_byte` для всех битовых значений входного состояния;
- вложенные `phi`, удалённое изменение поля, безусловный increment и trap другого поля;
- цепочки из 12 ромбов, включая изменение поля в начале, середине и конце.

Получено **9 UNSAT**, а два явно заданных отрицательных контроля дают **SAT**:
неправильное forwarding изменённого поля и удалённый обязательный overflow guard.
Результат повторён Z3 5.3.1 CLI и закреплённым Z3 4.15.4 Python. Это проверка выбранных
unsigned/acyclic функций в поддерживаемых семантиках, не доказательство soundness
всего pass или LLVM. Неизвестные инструкции отвергаются; статусы Verified не расширены.

На Apple M4 / Clang 23.1.4 полный набор компилятора прошёл: **411 тестов,
11 платформенных skips**. Дополнительная финальная проверка нового набора также
прошла. CI использует существующий `Aggregate lowering correctness`: native O0/O2
на Linux/macOS/Windows, SMT на Linux с pinned solver. Тяжёлый aggregate benchmark
по-прежнему выполняется только на Linux. Удалённые результаты нужно проверять
для конкретного HEAD; локальный успех не объявляется приёмкой Windows/Linux.

## Стоимость и сохранение результата P3

Production JSON прошёл 6785 partition cases на каждый executable O0/O2 и Rust,
492 CLI checks. Raw LLVM **побайтово совпадает** с кандидатом P3; Mach-O `.text`
совпадает по SHA-256 (`df140b4587f7d67201381590a67f425785a446a298479fa220987f420e061aed`).
Алгоритм и target прежние, `.text` — 7204 байта. Повторного throughput-измерения
здесь нет: +11–24% остаётся результатом сохранённой серии P3, а не новой серии P3-P.

Отдельный диагностический замер Python `llvm()` на уже построенном JSON SIR:
20 перемешанных повторов, медиана 11,39 мс без анализа и 11,97 мс с ним. Это около
0,59 мс дополнительных затрат только на эмиссию; parsing, Clang и linking не входят.
Не следует интерпретировать это как стабильный процент overhead всей компиляции.

## Воспроизведение

```sh
python -m unittest discover -s tests -p test_field_forwarding.py -v
python -m pip install -r verification/requirements.txt
python tools/check_field_forwarding.py --python-z3 --output build/field-forwarding
```

Для проверки точного соответствия сохранённому P3, после подготовки reference
по инструкции [исследования](guard-cfg-investigation.md):

```sh
PYTHONPATH=. python benchmarks/guards/accept_production.py \
  --reference /tmp/p3-reference --p3 /tmp/p3-results --output /tmp/production-check
```

Эта проверка Mach-O выполняется на macOS с тем же Clang/target, что P3. LLVM major
version сама по себе не гарантирует совпадения кода при другой patch-версии.

[Локальная приёмка и хеши](https://github.com/rulerom/liza/tree/field-forwarding/benchmarks/guards/results/production-macos).
R0/VN0 для Network Gateway сохраняют стратегический приоритет; интеграция не добавляет
новые возможности borrowing, циклический анализ или общую range analysis.

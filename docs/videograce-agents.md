# VideoGrace agents: orchestration и inference

Первичная цель — перенос управляющей логики агентов на Liza с сохранением
реальных контрактов VideoGrace. Удаление Python из агента и удаление Python
из исполнения моделей — разные результаты. Python backend может оставаться
отдельным компонентом; это ещё не означает отсутствие Python во всём deployment.

## Порядок работ

1. Process API и минимальные файловые операции — независимый системный срез.
2. Recorder: одно назначение, один native Recorder, один Reactor; локальный MP4,
   heartbeat и остановка по stop/cancel/disconnect.
3. Recorder production finalization: отчёт, Storage, подтверждённые finalizing и
   artifact_ready, завершение и условное удаление локальных файлов.
4. Summarizer: прикладной CAN/control клиент, получение транскрипта конкретного
   сеанса, вызов выбранного backend и подтверждённая публикация результата в чат.
5. Transcriber и Translator: отдельные аудиты медиатранспорта и inference,
   затем узкие рабочие срезы. Их взаимный порядок пока не закреплён.

На момент фиксации плана [CAN Echo Worker #94](https://github.com/rulerom/liza/pull/94)
и [Process API #95](https://github.com/rulerom/liza/pull/95) представлены отдельными
PR. Echo прошёл положительный live-обмен с demo; Process API имеет платформенную
приёмку. Это не означает готовность Recorder Agent или переноса всех сервисов.

## Что установлено по исходникам VideoGrace

Аудит 16 ноября 2026: `VIP/examples/06-recorder`, `VIP/examples/09-summarizer`,
`Services/Transcriber/transcriber.py`, `Services/SpeechTranslator/translator.py`.
Ниже — поведение этих исходников, не обещание доступности всех компонентов на
любом установленном сервере. Модели для аудита не запускались и не загружались.

| Сервис | Текущая граница backend | Следствие для Liza |
| --- | --- | --- |
| Recorder, consolidated_native | Один native Recorder, argv и child env; штатный stop marker; консолидация встроена | Process API достаточен для запуска/наблюдения, но полный агент требует файлов, Storage и CAN receipts |
| Summarizer, режим по умолчанию | summarizer.py передаёт prompt через stdin и получает результат из stdout; local_summary.py запускает закреплённый native LLM runtime | #95 без pipes не заменяет этот обмен; потребуются отдельно bounded IPC или явно выбранный model-server |
| Summarizer, HTTP-режим | openai_compatible_summary.py вызывает HTTPS Chat Completions, stream=false; режим включается оператором | Возможен первый HTTP-срез, но он не заменяет локальный режим и не включается автоматически |
| Transcriber | mlx_whisper либо cached faster_whisper.WhisperModel загружается в Python-процессе | Перенос CAN/RTP не переносит inference; нужен отдельно выбранный runtime/ABI/model-server |
| Translator | Постоянный CommandBackend: JSON lines через stdin/stdout, warmup, text и PCM s16le/base64 | Нужны отдельный контракт IPC, cancellation, аудиобюджеты и RTC; общего spawn/wait недостаточно |

Имеющаяся локальная LLM Summarizer уже использует native runtime; не следует
исходить из того, что всем четырём сервисам обязательно нужен Python для inference.
При этом подготовка модели, runtime, кэша и проверка ресурсов тоже являются
частью действующей Python-обвязки и требуют отдельного плана переноса.

## Общая CAN-модель

Не создавать четыре копии Echo Worker. При переносе второго и третьего
приложений извлекать подтверждённо общие части: session lifecycle, registration,
heartbeat/reconnect, assignment identity, cancel, события и receipt correlation.
`can.Session`, `can.Assignment`, `can.Events` — рабочие названия направлений,
не объявление уже существующего стандартного API.

Протокольные основы остаются общими, а бизнес-политики — прикладными:

- identity назначения включает connection generation, job_id и assignment_id;
- поздний результат старого назначения не публикуется в новой сессии;
- обычное событие не получает вымышленный универсальный ACK;
- подтверждаемые finalizing/artifact_ready требуют конкретного receipt;
- disconnect-политика определяется контрактом сервиса: для Recorder остановить
  медиа и сохранять неподтверждённые артефакты; универсальное немедленное
  cancelled для всех сервисов не вводится;
- общая библиотека не должна фиксировать echo-specific payload, лимит текста
  512 байт или бизнес-статусы одного приложения для всех агентов.

Универсальный framework заранее не строится. Сначала выделяется повторяемое
поведение работающих приложений, затем стабилизируются его интерфейсы.

## Граница inference и критерии готовности

Для каждого сервиса отдельно сверить фактический режим поставки: HTTP API,
native executable, Python-библиотека или отдельный model-server. Выбор C ABI,
native backend или сервера делается после этого аудита, с измерением стоимости
передачи данных, памяти, загрузки модели и отмены. Прямые MLX bindings и общий
inference runtime не являются следующей автоматической задачей Liza.

Контракт backend должен определять лимиты входа/выхода, readiness/warmup,
timeout и cancel, идентичность запроса и запрет публикации позднего результата.
Секреты и содержимое транскриптов не попадают в argv или диагностические логи.
Передача транскрипта внешнему провайдеру требует явной конфигурации оператора;
не следует менять действующий локальный режим на внешний API по умолчанию.

Первая HTTP-версия Summarizer должна обслуживать CAN, пока ожидает модель,
поддерживать необходимые POST/headers/body и объявленные размеры ответов.
Текущие экспериментальные HTTP/JSON-клиенты с малыми буферами нельзя объявлять
готовым LLM-клиентом без этого расширения. Получение транскрипта и подтверждение
сообщения в чате тоже входят в срез; одной успешной HTTP-генерации недостаточно.

Успех Recorder разделяется на «получен локальный MP4» и «артефакт опубликован и
подтверждён сервером». Успех Summarizer — на «модель вернула текст» и «результат
нужного назначения подтверждён в чате». Удаление файлов или выдача completed
не должны опережать требуемое прикладное подтверждение.

SG5 остаётся отложенным до измеренной дорогой операции, которую действительно
нужно распараллеливать внутри Liza. Внешний inference процесс или сервис сам по
себе не требует добавления общего worker pool в язык.

# Потоковая проверка и форматирование JSON

`liza-json check` — первый прикладной шаг Text & Compiler Foundations.
Валидатор написан на Liza; он не строит дерево и не сохраняет текст токенов.
Новые операции runtime и изменения модели владения не требуются.

```sh
python3 -m liza build examples/apps/liza_json.liza --project-root examples -o build/liza-json
./build/liza-json check config.json
./build/liza-json format config.json > formatted.json
```

На Windows используйте `build/liza-json.exe`. Успешный `check` печатает `OK`;
`format` печатает только форматированный JSON. Не перенаправляйте stdout
в исходный файл: shell обнулит его до запуска программы. CLI usage также
напоминает, что вывод потоковый и при ошибке может остаться неполным.

## Профиль входа

Основа — [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259).
Корнем может быть любое JSON-значение. Повторяющиеся ключи разрешены.
Пробелами считаются только SP, TAB, CR и LF. Комментарии, завершающие
запятые, NaN и Infinity отклоняются. BOM в начале документа отклоняется.

Весь вход должен быть корректным UTF-8. Escape-последовательности проверяются,
включая пары UTF-16 суррогатов. Одиночный суррогат отклоняется: это намеренно
более строгий профиль Unicode scalar values, чем ABNF RFC, допускающая
непарные суррогаты. Не-символы Unicode не запрещены; `\u0000` допустим.

Числа проверяются **лексически**, без преобразования в `f64` или целое число.
Длина числа, строки или файла не ограничена размером чанка. Общий счётчик
входа ограничен `u64`; превышение возвращает `SizeOverflow`.
Глубина контейнеров ограничена 64: 65-я открывающая скобка даёт `DepthLimit`.
Это ограничение ресурса, а не утверждение о синтаксической неверности JSON.

## Библиотека

| Операция | Результат |
| --- | --- |
| `json.create()` | Независимое значение `JsonState` |
| `json.feed(state, data:View<u8>)` | Новое состояние, без удержания view |
| `json.status(state)` | `Option<JsonError>`: обнаруженная ошибка или `None` |
| `json.finish(state)` | `Result<u64,JsonError>`: число байтов либо ошибка |

`None` не означает завершённый документ. `finish` проверяет EOF как снимок:
после незавершённого снимка можно продолжить `feed`. Обнаруженная при `feed`
ошибка сохраняется неизменно; дальнейшие данные игнорируются. Поля состояния
закрыты. Состояние можно копировать; оно не зависит от времени жизни чанка.

`JsonError` содержит `kind` и `offset`. Смещения — абсолютные, байтовые,
с нуля. Ошибка синтаксиса указывает на отвергнутый байт; незавершённый документ
— на конец входа. Ошибка UTF-8 указывает на начало некорректной последовательности.
Непарный суррогат указывает на обратную косую черту первого `\u`.
Некорректная hex-цифра указывает на саму цифру.

Проверка UTF-8 выполняется перед синтаксическим переходом для каждого байта.
Первое обнаруженное нарушение сохраняется независимо от разбиения входа.
На EOF незавершённый UTF-8 имеет приоритет перед незавершённым JSON.

## Стоимость и CLI

Стек содержит 64 однобайтовых состояния. Остальные поля — скалярные состояния
лексического и UTF-8 автоматов. Память валидатора не растёт вместе с входом;
CLI читает `file.read_chunk` по 2048 байтов. Нет heap-аллокаций валидатора,
накопления токенов или декодирования строк. Передача состояния по значению
может копировать фиксированный стек; zero-copy исполнения не обещается.

| Код выхода | Значение |
| --- | --- |
| 0 | Документ принят |
| 1 | Синтаксис, UTF-8 или Unicode escape отвергнут |
| 2 | Неверная командная строка |
| 3 | Ошибка открытия, чтения, закрытия или вывода |
| 4 | Лимит глубины или размера |

Файл закрывается на всех нормальных путях после открытия, в том числе при
ранней ошибке JSON. Ошибка закрытия имеет приоритет над результатом проверки.
Диагностика имеет вид `InvalidNumber at byte 12` и выводится в stderr.

## Проверка и границы

Нативные тесты O0/O2 подают данные во время исполнения, проверяют разбиения
внутри UTF-8, escapes, суррогатных пар и чисел, EOF, границы глубины и длинные
токены. Генерируемые документы дополнительно сопоставляются с Python JSON.
Это тестирование, не новый эксперимент Verified и не доказательство всех входов.

API `json.*` остаётся валидатором синтаксиса, **не tokenizer с выдачей событий**
и не DOM. Отдельный форматтер ниже использует его без изменений. Строковые значения не декодируются наружу.
Будущему tokenizer потребуется различать исходный диапазон и декодированный
текст, особенно для escapes и строк, пересекающих чанки.

## Format

`liza-json format <file>` меняет только JSON whitespace вне строк.
Отступ — два пробела; непустые контейнеры многострочные, пустые — `[]` и `{}`.
После двоеточия один пробел, в конце успешного документа один LF.

Сохраняются порядок и повторяющиеся ключи, написание чисел (включая `-0`,
экспоненту и произвольное число цифр), все строковые escapes и исходный Unicode.
Это не canonical JSON: `"\u0061"` не заменяется на `"a"`, значения не декодируются
и числа не преобразуются в floating-point.

Форматтер расположен в обычном модуле `examples/text/json_format.liza`.
Он содержит приватный копируемый `State` и принимает байты через
`feed_byte(borrow mut state, byte)->Result<Piece,JsonError>`.
Сначала вызывается существующий валидатор, затем формируется кусок вывода.
`finish(borrow state)` проверяет EOF, не изменяя снимок состояния.
Публичного tokenizer, DOM и новых операций компилятора/runtime нет.

Каждый Piece содержит массив 132 байта и длину. Это верхняя граница одного
перехода: LF, до 128 пробелов и текущий знак. До четырёх байтов незавершённого
UTF-8 scalar хранятся отдельно. Piece с данными содержит самостоятельную UTF-8
последовательность; String никогда не получает половину кодовой точки.

CLI читает чанки 2048 байта и один раз выделяет региональный выходной String
вместимостью 2048 байта. Если места для следующего Piece недостаточно, содержимое
передаётся в stdout, String очищается и используется повторно. В цикле нет
выделения пользовательских буферов. Стек валидатора ограничен глубиной 64;
истории токенов не накапливаются. Это 2 КиБ выходной вместимости и 2 КиБ
логического входного чанка, **не оценка всего RSS или stack frame**: метаданные,
копии фиксированных структур при lowering и системные буферы учитываются отдельно.

Formatter не заявляет zero-copy или производительность mutable JSON benchmark.
Он вызывает value-based валидатор на каждом байте и переносит готовые куски в
String. Оптимизация этого пути — отдельная измеряемая задача.

### Ошибки и частичный результат

Коды выхода и байтовые смещения совпадают с check. До EOF нельзя считать
документ принятым. При поздней синтаксической ошибке в stdout уже может находиться
префикс результата; содержимое, ещё не отправленное из String, отбрасывается.
При ошибке вывода возможен частичный системный write, в том числе внутри UTF-8
последовательности. Автоматического повторения, rollback и атомарной замены файла нет.

Файл, String и регион освобождаются на всех нормальных ветвях. Ошибка закрытия
файла имеет приоритет; ошибка чтения или stdout возвращает 3. CLI не выводит
`OK` после format.

Нативные O0/O2 тесты проверяют точный layout и lexemes, idempotence, сопоставление
с независимым Python pretty-printer на генерируемых документах, границы чанков
в Unicode и escapes, длинные числа и строки, глубину 64/65, ошибочные входы,
снимки состояния и закрытый stdout. Приёмка не расширяет гарантии Verified.

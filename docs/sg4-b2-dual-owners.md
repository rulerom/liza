# SG4-B2: Dual UDP RTP Owners

B2 — прикладной эксперимент поверх [B1](sg4-b1-multiple-groups.md).
Компилятор и production runtime не изменяются. Два consumer используют
существующий `groups.run_pair`, отдельные UDP endpoints и локальные таблицы
получателей. Межгрупповых очередей и передачи пакетов между workers нет.

## Методика

Оба варианта написаны на Liza и используют один RTP parser и fanout helper.
Single-вариант принимает два SSRC через один endpoint и обслуживает две таблицы.
Dual-вариант имеет отдельный endpoint и таблицу для каждого потока. В обеих
конфигурациях два генератора и два независимых collector, одинаковые списки
получателей и суммарное число ожидаемых fanout-копий.

Первые проверки останавливают A или вводят её локальный sticky notification
fault в середине серии B. События native join, receipt, handback и destroy
записываются с generation и порядковыми номерами. Collector B должен наблюдать
пакеты, предложенные генератором после cleanup A. Время, проведённое в
`groups.run_pair`, всё ещё охватывает обе группы; промежуточного результата B
языковому owner API не предоставляет.

Нагрузочные профили `(A, B)` — `(0, 2000)`, `(2000, 2000)`, `(5000, 5000)`,
`(10000, 2000)` RTP/с. Последний является асимметричной предложенной нагрузкой;
перегрузка определяется по наблюдаемому недоприёму, а не по числу в конфигурации.
Основная серия: 1200 байт, 64 получателя на поток, пять секунд и пять повторов,
с чередованием порядка single/dual. Для обоих генераторов задан общий будущий
CLOCK_MONOTONIC start. Конфигурация и бинарники фиксируются SHA-256 на всю серию.

## Границы выводов

В single-варианте одна UDP receive queue, в dual — две. Изменяются и число
сетевых владельцев, и суммарный ресурс очередей ОС. Поэтому результат относится
к конфигурации целиком и не измеряет чистое масштабирование CPU. Два bind-адреса
не доказывают изоляцию физических NIC; маршрутизация и аппаратные интерфейсы
требуют отдельного эксперимента.

Изоляция владения не гарантирует изоляцию задержек или CPU. Генераторы,
collectors, файловый I/O и все groups конкурируют за один хост. Вместе с p99
обязательно сохраняются фактическая доставка, её доля и счётчики входного
недоприёма, локальных send и наблюдений collector. Успех send не означает
доставку. Системные UDP counters не дают per-socket атрибуции.

Функциональная приёмка выполняется на Linux/macOS. Runtime Windows проверен в
B1; POSIX benchmark не выдаётся за новый Windows workload. Порогов throughput
или latency в CI нет.

[Исходники и воспроизведение](https://github.com/rulerom/liza/blob/sg4-b2-dual-owners/benchmarks/sg4-dual/README.md)
описывают фазы, bounded recording, управляющие потоки стенда, ресурсные лимиты
и сохранение артефактов. SG5 и динамическое управление группами в этот этап не входят.


## Apple M4: результаты первой серии

macOS 26.4.1 (25E253), Apple M4, 10 физических/логических ядер, 16 GiB RAM.
Сборка — Apple clang 21.0.0 (`clang-2100.1.1.101`), `-O2`,
`arm64-apple-darwin25.4.0`. Серия содержит 42 прогона: два функциональных сценария и 40 нагрузочных.
Исходники приложения зафиксированы в `cfaf8d4`, используются одни и те же
single/dual бинарники и два collector на всю серию. LLVM/compiler version,
команды, SHA-256 и сгенерированная конфигурация сохранены в manifest.
Это пять коротких повторов на одном хосте, без статистического утверждения
об универсальном пороге capacity.

### Изоляция завершения и локального отказа

При 2k/2k A завершает offer через 2.5 секунды, затем проходит stop или
инъекцию sticky notification fault. После A destroy генератор B предлагает
ещё 4683 пакета в stop-сценарии и 4682 в fault-сценарии. Collector наблюдает
все соответствующие 299712 и 299648 копий; p99 этой части B — 0.4 мс.
Результаты групп — `Ok/Ok` и `Faulted/Ok`. В обеих группах подтверждены три
native joins, receipts и handback до destroy.

Это функциональное свидетельство независимых lifecycle на данном сценарии.
Оно не обещает продолжение B после process-fatal исхода A и не является
вероятностной гарантией задержек при произвольных отказах.

### Когда dual оказался полезен

- При 0+2k throughput одинаков: второй сетевой владелец не добавляет полезной
  пропускной способности. Разброс p99 не позволяет объявить универсальный
  выигрыш latency: single B 0.4–6.4 мс, dual B 0.5–2.0 мс по пяти повторам.
- При 2k+2k доставка полная в обеих конфигурациях. В этой серии dual имеет
  меньшую медиану p99 B, ценой большего CPU. Диапазоны отдельных p99 пересекаются:
  single B 0.9–29.0 мс, dual B 0.5–3.9 мс; строгой QoS-гарантии нет.
- При 5k+5k медианное **парное** отношение доставленного throughput — 1.562,
  а CPU service — 1.977. Dual принимает больше, но хвост задержки выше и
  недоприём остаётся. Удвоения throughput не получено.
- При 10k+2k B имеет полную доставку во всех пяти dual-повторах. У single
  медиана B — 35.44%, минимум — 31.53%. При этом B p99 в dual 3.0–25.9 мс,
  против 0.5–2.0 мс в idle-A dual control: нагрузка A всё ещё влияет на B.
  Владение изолировано, CPU/latency не изолированы жёстко.

В конфигурации dual изменилось и число receive queues: SO_RCVBUF каждого
endpoint — 786896 байт, общий ресурс входных очередей удвоен. Поэтому данные
поддерживают полезность разделения сетевых владельцев и очередей для этой
нагрузки, но не отделяют эффект второго CPU от разделения очередей. Причину
разброса p99 по одному этому эксперименту установить нельзя.

### Где наблюдался недоприём

Во всех 42 прогонах локальные fanout send failures равны нулю; число
наблюдавшихся копий совпало с успешными локальными отправками. Для каждого
прогона прирост системного UDP full-buffer counter совпал с суммой входных
недоприёмов A и B. Необъяснённого дефицита записей collector в этой серии нет.
Это согласуется с переполнением входных UDP queues, но глобальный counter
не является per-socket доказательством и не объясняет историческую паузу A2.

Все collector cutoff snapshots пусты; это не исключает теоретически более
позднее прибытие. Наибольший store wall interval — 33.677 мс. Генераторские
phases, max interpacket gaps, collector timings, CPU, per-receiver coverage и
полные latency histograms сохранены, чтобы результат не сводился к одному p99.
Например, при 5k+5k медианный суммарный CPU collectors — 5.43 с в single и
10.08 с в dual, CPU генераторов — 0.78 и 1.29 с. Стоимость внешнего стенда
растёт с наблюдаемой нагрузкой и не исключена из конкуренции за хост.

### Ресурсы и воспроизведение

| Ресурс | single | dual |
| --- | ---: | ---: |
| Участники scoped-групп | 3 | 6 |
| Инициализированные process-lifetime reapers | 1 | 2 |
| Дополнительные pair owner threads | 0 | 2 |
| Управляющие threads стенда | 2 | 3 |
| Запрошенные стеки участников | 3 MiB | 6 MiB |
| Запрошенные стеки reapers | 1 MiB | 2 MiB |
| Запрошенные стеки pair owners | 0 | 2 MiB |
| Managed budget групп | 64 KiB | 2 × 64 KiB |
| Отдельный Reactor budget | 64 KiB | 2 × 64 KiB |
| Отдельный Region budget | 4 KiB | 2 × 4 KiB |

Статическое observation storage стенда — 2562000 байт в обоих вариантах;
process-level SG2 metadata pool — 416 байт на этой ABI. Это не точный RSS:
OS buffers, default stacks harness threads и другие накладные расходы ОС
учитываются отдельно. После joins общий live socket count каждой группы — 0;
максимальное наблюдённое время stop intent → destroy — 5.379 мс.

[Архивы отчётов и provenance](https://github.com/rulerom/liza/blob/sg4-b2-dual-owners/benchmarks/sg4-dual/results/README.md)
содержат raw counters и SHA-256. Исходники, бинарники и сжатые packet records
сохранены также вне temporary-каталога, в gitignored
`build/sg4-b2-macos-cfaf8d4` рабочего репозитория. В provenance явно отмечено,
что git commit завершился после начала build: все 53 repository source hashes
проверены против `cfaf8d4`, десять generated hashes и четыре binary hashes
совпали. Код приложения в течение измерений не менялся.

B2 даёт первый ответ для этого хоста: один владелец достаточен на младшем
профиле, два полезны для разделения асимметричных потоков и увеличивают
наблюдаемую capacity на старших профилях с дополнительной CPU-стоимостью.
Физические NIC, длинные серии и отдельные машины генерации/сбора остаются
отдельной проверкой. Из этих данных не следует необходимость SG5.

# RTSP: длительный прогон

17 ноября 2026 года существующий RTSP → VideoGrace процесс на Apple M4
прошёл контрольную точку **6 ч 54 мин uptime**. Это отдельный endurance
milestone после [оптимизации копий parser](rtsp-client.md#parser),
а не новый тест предельной производительности.

**Первый процесс перестал наблюдаться до 24 часов. После приёмки байтовых
литералов запущен новый процесс и отдельное наблюдение. Итог 24 часов
ещё не получен.**

## Наблюдаемый процесс

Камера передаёт H.264 через RTSP interleaved TCP; коннектор публикует его
в `radio` на `demo.videograce.ru` как обычный WSS-клиент. Декодирования,
транскодирования и внешнего медиапроцесса нет. Запуск состоялся
16 ноября в 19:15:33 Asia/Tomsk (12:15:33 UTC).

Работает O2-бинарник с оптимизацией #100 и экспериментальным `run_ms: 0`
из отдельного PR #101. Это не бинарник прежних конечных AB/BA-серий.
SHA-256:
`2ff538c7114e1a4ad198f7c0a45bcb54848313c40b726a039f3e99d08423a8a0`.

| Наблюдение около 6 ч 54 мин | Значение |
| --- | ---: |
| RSS, текущий снимок | 7024 КиБ (6,9 МиБ) |
| Накопленное CPU time | 5292,31 с |
| CPU time / uptime | 0,213 ядра |
| Сетевые сокеты | 2 TCP ESTABLISHED, 1 UDP |
| Поток байтов ОС, короткий интервал | около 2,6 Мбит/с в каждую сторону |
| Накопленные байты ОС | около 7,8 ГБ в каждую сторону |

Снимок не показывает роста памяти во времени и сам по себе не доказывает
отсутствия утечек. Текущий RSS нельзя непосредственно сравнивать с maximum RSS
14,9 МиБ в коротких сериях. CPU time / uptime — среднее всего процесса;
`ps %CPU` показывает отдельную недавнюю оценку.

Счётчики ОС включают транспортный/control-трафик: это не число RTP-пакетов
и не подтверждение доставки зрителю. Непрерывное наличие движущегося видео
во всех точках семичасового интервала инструментально не проверялось.

## Наблюдение до 24 часов uptime

Внешний read-only наблюдатель `tools/monitor_rtsp_endurance.py` запущен
17 ноября в 02:21:22 Asia/Tomsk, при uptime 7 ч 5 мин 49 с. Он снимает
показатели раз в 300 секунд, проверяя PID, время запуска и команду процесса
до и после сбора. Первые семь часов не восстанавливаются задним числом.
Первый машинный снимок сохранён в
`benchmarks/rtsp-parser/endurance/checkpoint-2026-11-17.json`.

Цель — 24 часа uptime, то есть 17 ноября в 19:15:33 Asia/Tomsk
(12:15:33 UTC), если процесс продолжит работу. Это не 24 часа покрытия
наблюдателем. Он не посылает сигналов, не перезапускает приложение и при
достижении цели завершает только собственную работу. Обрыв соединения может
завершить сам коннектор: автоматический reconnect не добавлен.

Первый прогон не достиг этой цели. Наблюдатель записал пять снимков,
затем статус `process_no_longer_observed`. Последний успешный снимок —
17 ноября 02:41:23 Asia/Tomsk, uptime **7 ч 25 мин 50 с**. Диапазон
наблюдённого RSS — 6,58..6,81 МиБ; последние накопленные счётчики ОС —
8,384 ГБ входящих и 8,345 ГБ исходящих байтов. Точный момент, причина и
exit status завершения неизвестны: stdout оставался в пользовательском
терминале. Агент не отправлял сигналов старому процессу. Это не успешная
24-часовая приёмка и не доказательство отсутствия утечек.
Итог наблюдателя сохранён в
`benchmarks/rtsp-parser/endurance/original-observer-final-2026-11-17.json`.

Для другого существующего процесса на macOS:

```sh
python3 tools/monitor_rtsp_endurance.py \
  --pid PID --binary /absolute/path/liza-rtsp \
  --output /private/tmp/rtsp-observation \
  --interval-seconds 300 --target-uptime-seconds 86400
```

Выходной каталог должен быть новым. Нужны разрешения macOS на чтение
показателей процесса через `ps`, `lsof` и `nettop`. Наблюдатель работает
отдельно от медиатракта; это диагностический Python-инструмент, а не часть
нативного приложения Liza.

Для текущего запуска локальные файлы находятся в
`/private/tmp/liza-rtsp-endurance-24h/`:

- `metadata.json`: идентичность бинарника, начало покрытия и целевой uptime.
- `samples.jsonl`: UTC timestamps, uptime, RSS, накопленное CPU time,
  интервальная доля ядра, FD/сокеты, байтовые счётчики и ошибки инструментов.
- `summary.json`: текущий статус, первый/последний снимки, наблюдённый
  диапазон RSS и максимальный интервал между снимками.

Пароль и содержимое конфигурации не записываются. `target_uptime_reached`
означает только достижение времени жизни процесса. Для итогового отчёта
нужно отдельно проверить ошибки сбора, промежутки между снимками и динамику
RSS/CPU/трафика. Сон машины или задержки инструментов не считаются покрытым
непрерывным измерением.

Текущий замороженный бинарник выводит RTP inputs/send/sequence discontinuities
только при штатном завершении. В live-снимках эти поля равны `null`:
они не заменены нулями или оценкой из байтов. Наблюдатель не читает терминал
пользователя и не останавливает поток ради получения финальных счётчиков.
Если позднее произойдёт штатная остановка, итог приложения следует сохранить
отдельно. Без него нельзя утверждать отсутствие sequence gaps за весь прогон.

После локальной приёмки новой сборки пользователь попросил заменить клиент.
На момент проверки прежний PID уже отсутствовал; другого RTSP-коннектора
не обнаружено. Новый O2-бинарник запущен 17 ноября в **02:54:50 Asia/Tomsk**
(16 ноября 19:54:50 UTC), с той же локальной конфигурацией и `run_ms: 0`.
Публикация в `radio` подтверждена пользователем: видео есть и движется.
Новый запуск не является продолжением uptime первого процесса.

Сборка из revision `2dca69d448ec66dc526469de60b68c8fd7076376`:
`d8f2e598d2fcfc616b9b2f3f69c83aa0c25a74255e49261db7e41a592ab9bc97`
(SHA-256 бинарника). В RTSP используются [байтовые литералы](byte-literals.md);

546 тестов общего набора, 45 штатно пропущены, ошибок нет; отдельно пройдена

Новый observer снимает показатели с начала запуска раз в пять минут до

`/private/tmp/liza-rtsp-byte-literals.log`, чтобы при штатном завершении

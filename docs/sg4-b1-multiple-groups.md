# SG4-B1: Multiple Active Groups

Статус: контракт следующего этапа; реализация ещё не начата.
Критерий успеха — независимое владение и завершение двух одновременно
активных scoped-групп. Прирост packets/sec не является критерием этого этапа.

## Порядок работ

| Этап | Результат и условие перехода |
| --- | --- |
| SG4-A | Завершить benchmark и расследование collector (#82 → #83 → #84); сохранить исходные измерения и ограничения стенда |
| SG4-B1 | Несколько активных групп: изоляция ресурсов, адресация операций, независимые shutdown, join и handback |
| SG4-B2 | Прикладная конфигурация нескольких сетевых владельцев: Reactor, сокеты или NIC |
| SG5 | Bounded Compute Workers для конкретной измеренной тяжёлой операции |

Простой RTP fanout сохраняет одного сетевого владельца как baseline.
410–420 тысяч успешных локальных отправок/с — результат исследованного
локального стенда, а не предел worker, сетевой карты или гарантия доставки.
SG4-B посвящён параллелизму I/O; SG5 — параллелизму вычислений.

## Владение и адресация

Каждая группа владеет FIFO, data/control wake sources, deadline и stop intent.
Consumer владеет своим Reactor и сетевыми сокетами. Region/Buffer сохраняют
своего определённого owner. Общая инфраструктура координирует группы, но
не получает права закрывать сокеты или освобождать память живого участника.
Глобальный supervisor не является обязательным новым компонентом B1.

Каждый вызов `groups.*` должен однозначно определять группу. Контекст callback
может задавать группу неявно, если runtime проверяет принадлежность потока,
роль и срок жизни контекста. Для owner-операций требуется столь же однозначная
адресация. Неоднозначного глобального active-group быть не должно.
Окончательный языковой синтаксис и механизм запуска нескольких групп требуют
отдельного решения реализации; этот документ не объявляет их существующими.

## Нормативные инварианты

1. Остановка A не меняет состояние, readiness, FIFO, wake sources и ресурсы B.
2. Операции адресуются одной группе; чужой или истёкший контекст отклоняется.
3. Receipt содержит идентичность группы/слота, generation и участника.
   Receipt A нельзя принять за join B или следующего поколения того же слота.
4. Освобождение A разрешено только после реальных joins всех пользователей
   её ресурсов и окончательного handback. `Exited` не заменяет join.
5. Локальный восстановимый отказ A не останавливает B. Process-fatal исход
   определяется отдельно и завершает процесс со всеми группами.

После принятого `Submitted` только join-service выполняет native join
переданных handles. До передачи определён rollback. Неопределённое подтверждение
не разрешает повторный join или повторную передачу handles вслепую.
`Returned` не равно `Free`: owner принимает handback, уничтожает предыдущую
группу и только затем разрешает reuse. Generation не заменяет handback.

## Независимое завершение и бюджет

Текущий SG2 использует один process-lifetime service, одну join-запись и
последовательные блокирующие joins. Простого снятия admission restriction
недостаточно. Ожидание живого участника A не должно лишать завершившуюся B
возможности получить собственные receipts, handback и выполнить cleanup до
process-fatal эскалации A.

Реализация должна выбрать ограниченный механизм независимого обслуживания
joins и явно объявить максимум одновременно активных групп. Исчерпание слотов
даёт определённый отказ admission без запуска callbacks новой группы и без
изменения существующих групп. Нельзя создавать неограниченное число reaper
threads или запросов ради устранения взаимной блокировки.

Машинно-читаемый бюджет включает managed bytes, FIFO, sockets, native handles,
участников и запрошенные стеки, join-записи и process-level service ресурсы.
После повторного создания групп занятые ресурсы возвращаются к установленному
уровню. OS socket buffers и RSS не выдаются за точный managed budget.

## Граница отказов

| Исход | Контракт |
| --- | --- |
| Startup failure A | Callbacks A не стартуют; созданные участники joined перед cleanup; B продолжает работу |
| Известный fault A, участники отвечают | Локальный shutdown, joins и cleanup A с сохранением причины отказа; B продолжает работу |
| A не подтверждает прогресс или завершение | `Unresponsive`; ресурсы A сохраняются; timeout не является разрешением destroy |
| Shutdown deadline / неисправность join infrastructure по fail-stop политике | Явный process-fatal исход; штатный cleanup и возвращаемый `Err` не обещаются |

Существующий SG2 `_Exit(86)` при невозможности безопасно завершить shutdown
остаётся process-fatal до явного изменения политики. Его нельзя описывать как
изолированный отказ группы. До эскалации B сохраняет свои правила владения;
после прекращения процесса никаких гарантий продолжения B нет.

## Приёмка

Две UDP-группы используют разные порты и идентифицируемый трафик. Журнал
содержит группу, generation, участника и монотонный номер события.

| Сценарий | Проверяемое свойство |
| --- | --- |
| A останавливается при непрерывном трафике B | B сохраняет свой endpoint и обрабатывает свои пакеты и команды |
| Notification fault A | При отвечающих участниках A завершается локально; B продолжает работу |
| B завершается раньше удержанной gate группы A | Receipts, handback и cleanup B не ждут освобождения gate A |
| Deadline A истёк при живом участнике | Нет ложного `Stopped`/destroy A; process-fatal политика проверяется в дочернем процессе |
| Частичный startup A при работающей B | Rollback A не затрагивает B |
| Повторное создание в освобождённых слотах | Старый receipt не подтверждает новую группу; ресурсы не растут |
| Перепутанный или устаревший receipt | Проверяющий механизм отклоняет неверную идентичность |
| Задержанный handback после joins | Reuse и destroy до передачи полномочий запрещены |
| Admission capacity исчерпана | Явный отказ новой группе; существующие работают |

Проверки используют управляемые gates и внешний timeout процесса. Отрицательные
мутации должны выявлять принятие чужого/stale receipt, преждевременный reuse
и destroy до joins/handback. Функциональная приёмка — Linux/macOS/Windows.
Нагрузочный трафик здесь проверяет изоляцию, а не доказывает отсутствие потерь
UDP или преимущество производительности.

## Граница SG5

Принятие задачи очередью передаёт ownership принимающей стороне системы;
оно не подтверждает начало или завершение вычисления. При отказе из-за полной
очереди owned-пакет остаётся у отправителя. Отмена требует определённого
извлечения queued-задачи или подтверждения завершения выполняющейся работы.
Бюджет охватывает вход, выполняемые задачи, результаты и reorder storage.

Для закрепления RTP-потока за исполнителем используется как минимум
`(session_id, SSRC, generation)`, при необходимости идентичность источника.
Это сохраняет порядок обработки принятых пакетов, но не исправляет UDP reorder.
SG5 начинается после измерения конкретной тяжёлой операции и цены handoff.

Общий dispatcher, work stealing, миграция callbacks, разделяемый Reactor,
автоматическое распределение потоков и вычислительный пул в B1 не входят.

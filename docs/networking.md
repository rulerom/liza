# Сеть и потоки: какую модель выбрать

Начните с задачи и числа владельцев ресурсов. Для простого сетевого сервиса
дополнительный поток не является обязательным. Реализованные варианты ниже
имеют разные контракты; общего динамического менеджера задач пока нет.

| Задача | Текущая возможность | Следующая страница |
| --- | --- | --- |
| Один UDP endpoint, последовательная обработка | `net.udp_*`, owned buffer и явное закрытие | [UDP](udp.md) |
| Один TCP-клиент или базовый echo | Move-only сокеты и частичные I/O | [TCP](tcp.md) |
| Несколько TCP-соединений в одном потоке | Reactor, readiness и bounded capacity | [Reactor](reactor.md) |
| Сетевой consumer с командами и управляемым shutdown | `groups.run`, скрытый consumer-owned Reactor | [Scoped-группы](scoped-groups.md) |
| Два независимых сетевых владельца | `groups.run_pair`, отдельные endpoints, ресурсы и join lanes | [Scoped-группы](scoped-groups.md#two-groups) |
| Несколько изолированных функций с scalar входом/результатом | `workers.run(1..8)` и локальные ресурсы | [Workers](scoped-workers.md) |
| Отдельный эксперимент обмена `u32` | `channels.run`, bounded SPSC | [Scoped-канал](scoped-channels.md) |

Runner выбирается на программу: текущий Semantic IR запрещает смешивать
`groups.run/run_pair` с `workers.run` или `channels.run`. Это разные
экспериментальные модели, а не взаимозаменяемые части общего scheduler.

## Практический маршрут

Для первого сетевого приложения изучите [Region/Buffer](regions.md), затем
[UDP](udp.md) или [TCP](tcp.md). Для работы с несколькими соединениями нужен
[Reactor](reactor.md); для команд, notification и ограниченного shutdown —
[scoped-группа](scoped-groups.md). Группа сама владеет служебными FIFO и wake
sockets, а consumer владеет сетевым состоянием.

Два consumer в `run_pair` не делят Reactor, таблицу получателей или mutable
буфер. Локальный отвечающий fault может завершить только свою группу.
Неподтверждённый shutdown остаётся process-fatal: независимое владение не
обещает продолжение второй группы после завершения всего процесса.

## Что уже измерено

[SG4-B2](sg4-b2-dual-owners.md) сравнил один и два Liza RTP owner на одном Mac.
При 10k+2k dual сохранил полную доставку B в пяти повторах; на младшем профиле
прироста throughput не было. Это результат конфигурации с отдельными queues,
а не гарантия изоляции CPU или latency. [Каталог измерений](benchmarks.md)
содержит методику, raw counters и ограничения.

Пул вычислительных workers с owned-пакетами относится к будущему SG5. Он не
следует автоматически из наличия нативных потоков: сначала требуется тяжёлая
операция приложения и измерение стоимости вычисления относительно handoff.

[История MT0–SG4](architecture-history.md) объясняет происхождение механизмов;
её не нужно читать для использования текущего API.
